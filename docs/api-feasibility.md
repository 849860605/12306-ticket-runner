# 接口查票重构与可行性验证

验证日期：2026-09-07。此次只读验证，没有新建、支付、取消真实订单，也没有解除旧任务的 UNKNOWN 保护。

## 结论与交付边界

- **接口查票可行，已实现并得到真实结果。** 匿名 HTTP 请求和 Docker 内生产查询客户端均返回了有效数据。
- **当前交付为混合模式**：接口循环查票 → 命中 → 浏览器重新查询并逐项复核 → 原有浏览器预订、提交和订单回查。
- **纯接口下单尚未实现、未验证**。查到余票、票价或识别到登录状态，都不能证明下单接口完整可用。当前接口传输层根本不允许请求下单地址。
- 尚不能证明提升稀缺票成功率，也没有足够样本证明端到端速度优势。页面二次复核增加命中阶段的工作，优化重点是无票期间的循环查询。

## 一手来源与实测

1. 官网 [查询页](https://kyfw.12306.cn/otn/leftTicket/init) 当日声明 `CLeftTicketUrl = 'leftTicket/queryG'`。实现只读取这个声明，不遍历猜测后缀，不跳转到任意返回地址。
2. 官网加载的 [查询脚本](https://kyfw.12306.cn/otn/resources/merged/queryLeftTicket_end_js.js?scriptVersion=1.95046) 显式说明结果字段的解析方式：车次第 3 列，上下车站代码第 6/7 列，时刻第 8/9 列，可预订状态第 11 列，席别余票第 24/25/29/30/31/32 列；第 39 列为包含席别与价格的定长段。这里的列号从 0 开始。
3. 同一官方脚本使用十字符价格段，第 1–5 位为价格的十分之一元整数。因此可以从同一余票响应得到报价，不需要轮询时额外请求每趟车的票价接口。只支持已验证的六种有座席别，不把二等包座、卧铺或无座当成二等座。
4. 对配置行程进行匿名查询，HTTP 200、成功 JSON，原始结果 15 行；严格限定深圳北 IOQ → 信阳东 OYN、08:30 后，生产解析器筛得 6 个车次。2026-09-10 G846 为 09:20 → 15:03，二等座报价 608.5 元。独立只读票价请求也返回 608.5 元；库存曾显示“有”和“19”，属于不同时间快照，不能代表现在仍有票。
5. 生产客户端单次 API 请求耗时样本：宿主机 1.418 秒，Docker 0.575 秒，均不包含首次初始化。研究脚本另有约 3–5 秒的响应样本。它们不是随机化对照或持续性能测试，不能据此宣传固定倍数加速。
6. [Playwright 文档](https://playwright.dev/python/docs/api/class-apirequestcontext) 明确 `BrowserContext.request` 与所属浏览器共用 Cookie。实现使用该机制，不向前端或日志导出 Cookie，不复制第三方账号凭据，不延长服务端会话有效期。机制可用不代表当前账号会话一定有效。

官方脚本中还能观察到登录检查和发起预订请求，但后续交易依赖当次会话、动态提交信息、乘车人核验与订单回查。此次没有调用创建订单的接口，不能认定其已跑通。

## 代码与保护

- `src/ticket_runner/query_api.py`：独立的只读客户端与解析器。只允许查询初始化、当前查询入口和只读登录检查；禁用重定向、传输自动重试；每次释放响应，不保存原始行中的订单令牌。
- `src/ticket_runner/browser.py`：按配置选择查询引擎；API 命中后必须在页面重新确认同一行程与席别，检查库存人数和预算后才可预订。页面库存变化会回到原有退避/查询循环，未进入提交阶段。
- `src/ticket_runner/config.py`：`query_backend: browser | api`；浏览器默认配置的旧指纹保持不变，旧 UNKNOWN 订单不会因升级失去保护。引擎切换产生不同配置指纹，且不会自动启动或清理任务。
- 页面提供“查票方式”选择，实时小窗区分“接口查票完成”和“页面复核候选票”。具体下单始终标注为浏览器。
- 查询结果不成功、非 JSON、字段变化、票价缺失、数量未知格式均不当成“无票”；限流退避，登录/额外验证暂停，不能通过换引擎绕过失败。提交结果不明依旧禁止重试。

## 复现

```bash
uv run ticket-runner --config config.yaml probe-api

# 仅在同数据卷没有其他执行器时运行；不执行 ensure_login，也不预订。
docker compose stop runner
docker compose run --rm --service-ports runner --config /config/config.yaml --data-dir /data probe-api --with-session --compare-browser --all-dates
docker compose up -d runner
```

`probe-api` 默认只查询第一个日期；`--all-dates` 串行查询全部日期，共用配置间隔。`--compare-browser` 再读取网页列表，比较时刻表与共同报价；顺序查询间库存可变化。它不注册任务、不修改旧订单，无论 `auto_submit` 是什么都不会下单。

## 查不到票故障修复（2026-09-07 晚）

现场复现为 `TargetClosedError`：原数据卷的 Chromium `SingletonLock` 指向前一容器，当前容器内没有 Chromium 进程。控制台即便选了 API，也在发送查询前启动浏览器，因此启动失败后始终得到空列表；独立匿名接口查询同时正常。

修复后 API 查询与只读监控仅启动 HTTP 客户端，需要页面操作才启动 Chromium。浏览器配置目录另加排他锁；仅对 Docker 下可确认失效的旧容器锁链接做清理，活动 socket、活动配置目录进程或无法确认的锁会保留。已在原数据卷验证旧锁处理后浏览器启动成功，未重置浏览器配置或 Cookie。

本地 Docker 控制台通过真实页面按钮查询深圳北→信阳东、08:30 后、9 月 10–11 日，得到 12 个车次日期组合，两天各 6 个。API 查询分别为 0.601 秒、0.685 秒（不含首次初始化及配置的 30 秒查询间隔）。查询前后容器 Chromium 进程数均为 0。G846 在 10 日查询时二等座 608.5 元、19 张；11 日暂无票，仍可选择监控。库存仅代表查询时刻。

155 项自动化测试、Ruff 和 JavaScript 语法检查通过。新增测试覆盖浏览器不可启动时仍可查票、浏览器关闭后的 HTTP 恢复、Cookie 交接、旧锁清理及活动锁保留、只读监控不登录、部分查询失败状态。两个断网 Docker + Chromium 合成下单/回查场景（API、browser）均通过，每次只提交 1 个模拟订单。隔离演示页实测可显示具体失败原因，再次查询成功后会清除错误并显示明确的空结果提示。
