# 速度设计与验证

目标是减少“余票已经可见”到“提交确认”的本地等待与人工点击，不能保证获得稀缺票，也不能改变官网库存或优先级。

## 已实现

- 开始时间前 `prepare_seconds` 秒检查登录和未完成订单。实际起售时间仍需按官网填写。
- 所有日期共用一个串行查询节拍：开始到开始至少相隔 `query_interval_seconds`，把上一查询的加载时间计入间隔。慢请求不并发、不补发积压请求。
- 示例使用 5 秒（校验允许的最小值）；生产环境如遇限流，应提高间隔。5 秒不是官网承诺允许的频率。
- 页面内每 50 毫秒检查一次查询结果是否到达；这只是读取本地 DOM，不是每 50 毫秒发送查票请求。取代原有最多额外 500 毫秒的等待。
- 查询命中后直接按已配置乘车人、票种、席别进入确认，不等待下一轮，不需要临时手填。
- 通知投递放到独立协程，Webhook 的网络等待不占用查询节拍。最终结果仍先持久化，再通知。
- 异常继续指数退避，验证/页面歧义停止，提交不明不重复下单；提速不移除这些检查。

## 能快多少

假设每次官网页面查询耗时 2 秒、有两个候选日期，且没有限流或登录中断：

| 调度方式 | 同一日期的检查间隔 |
| --- | --- |
| 旧方式：查完等 30 秒 | 约 64 秒 |
| 新方式：开始到开始 5 秒 | 约 10 秒 |

这是调度计算，不是官网实测或与真人的速度对照实验。两日期轮询时 5 秒不代表每个日期每 5 秒被查到。只守一个日期会更快发现该日期变化，但会放弃其他日期；不替用户擅自缩小日期范围。

人与自动程序都要等待官网和网络。程序通常能够减少选人、选席别和确认操作的人工时间，但熟练用户恰好在放票时点击，仍可能早于下一次自动查询。部署服务器也不一定比本地网络快。

## 查看实际耗时

```bash
docker compose run --rm -e ENABLE_DESKTOP=0 runner --data-dir /data timings
```

输出最近最多 10000 个阶段样本的平均、P95、最大耗时和结果类别；包含登录、订单检查、查询、预订表单、提交与回查、候选到结果。只读本地 SQLite，不联网查票。`unknown` 不能当作下单成功；合成测试耗时不能当作官网实测。

`tests/test_performance.py` 通过可控时钟验证：2 秒查询以 0/5/10 秒启动，7 秒慢查询以 0/7/14 秒启动；没有补发突发请求、无票时才等下一轮、有票即处理、出错仍退避、通知不在查询等待路径中。

完整断网浏览器验证：

```bash
docker run --rm --init --network none -e PYTHONPATH=/app/src \
  -v "$PWD/src:/app/src:ro" -v "$PWD/scripts:/diagnostics:ro" \
  --entrypoint python ticket-runner:local /diagnostics/verify_checkout_flow.py
```

不挂载真实账号数据卷；所有网页均由合成 HTML 提供，覆盖生产适配器的查询、选人、确认、无订单号的待支付核对和重启防重。它不证明无人干预真实抢稀缺票成功。
