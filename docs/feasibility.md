# 12306 个人 Docker 购票脚本：可行性调研

调研日期：2026-09-06。先完成本调研，再开始实现。

## 结论

有条件可行。采用单账号、浏览器页面操作、官方二维码登录、人工处理额外核验和付款的路线。当前证据支持实现查询和自动操作原型，尚不足以证明在用户目标服务器上稳定下单，也没有证据证明优于官方候补。

交付必须区分：代码/模拟测试通过、官网匿名查询通过、登录及只读订单检查通过、用户账号真实下单通过。只有最后一项能够证明实际订票链路。

## 本机官网观察

通过 Browser 技能操作浏览器访问官方页面，未登录、未创建订单、未付款。

- 官网查询页可以打开。输入框为 `fromStationText`、`toStationText`、`train_date`，结果容器为 `queryLeftTable`。
- 使用官网查询链接查询 2026-09-07 深圳北至南京南，读取到真实车次、起终站、出发时间和席别余票。
- 查询结果含深圳、福田、南京等同城其他车站，不能只按车次筛选；必须核对实际上下车站。
- 余票单元格的无障碍描述包含席别、票价、余票状态。数字、“有”、“候补”、“--”必须分别处理；缺少价格不能推测价格。
- 查询链接的站名/代码分隔逗号需要保持字面量，整体编码成 `%2C` 在本次观察中使表单显示异常站名。
- 官方入口跳转至 `https://kyfw.12306.cn/otn/resources/login.html`，可选择“扫码登录”。
- 搜索抓取结果含“自动提交”说明，但当前匿名可见页面未显示该入口，不能将隐藏模板或历史抓取视为当前可用能力。

## 实现决策

- YAML 配置 + Python 执行器 + SQLite 状态与通知发件箱 + Docker Compose。
- 使用真实浏览器操作页面；不直接复用旧项目的私有下单接口。
- 优先做成人、直达、指定席别购票。学生/儿童/特殊票、自动付款、自动候补付款和中转联购不纳入首版。
- 单实例执行，提交前持久化意图；结果不明就停止再次下单，转订单核对/人工处理。
- 查询演练不点击预订或提交，不产生真实订单。实际运行需用户填写真实需求并启用自动提交。
- 二维码在本地持久化目录输出；额外核验通过同一浏览器的远程桌面完成。容器远程桌面仅绑定本机地址，服务器通过 SSH 隧道访问。

## 尚待验证

1. 用户服务器的访问与核验表现；本机浏览器访问成功不代表服务器成功。
2. 用户扫码后的长时间会话有效期；本机 Docker 重建后的短时恢复已通过，保存会话不保证永久登录。
3. 登录后的乘车人选择、订单确认、票价复核和待支付订单结构；必须以真实页面验证为准，结构不匹配应停止。
4. 正式订票只能使用用户确实需要购买的行程，不能为测试创建无关订单。

## 实现后的验证记录

- 45 项离线测试通过：日期/车站/预算/余票筛选、成人票与乘车人核对、提交意图落盘、提交超时、数据库重开后的核对、禁止重复提交、配置变化保护、进程锁、通知失败重试、敏感 URL 日志保护、会话 Cookie 的权限/域名限制/恢复，以及已恢复登录时不再进入扫码页、订单空状态检查。
- 使用断网、不挂载账号数据卷的 Chromium 容器验证 6 个合成页面场景：空订单、其他标签、隐藏空提示、范围外提示、空提示与订单卡片并存、未知文案，全部通过。脚本为 `scripts/verify_order_dom.py`。
- Docker 基础镜像构建通过；容器以非 root 用户运行 Chromium、Xvfb 和远程桌面。
- 在 Docker 依赖环境中挂载当前源码执行 `probe`，对 2026-09-07 深圳北至南京南做一次匿名只读查询，解析出 36 个可预订席别报价；按指定车次、二等/一等座和 1000 元预算筛得 G698 二等座报价 764 元、显示余票 1。这是当时观察，不代表之后仍有票。
- 最终镜像 `ticket-runner:local` 构建通过；在 `--network none` 的容器内执行 `demo` 通过，模拟提交次数为 1。
- Compose 实际创建运行网络和持久化数据卷，本机远程桌面入口返回 HTTP 200。用户第一次扫码后，程序于 22:17 检测到官方“退出”入口，确认登录；未完成订单页面的初始识别逻辑超时。
- 单独持久化浏览器目录在这次容器重建后未恢复登录，headless 及与扫码时相同的有界面模式均未识别到登录。因此新增当前专用浏览器的官方 Cookie 原子保存/恢复，不改变有效期、不打印凭据。
- 补充只读检查证明：保存的会话可直接打开官方订单页面，但直接重新打开扫码入口不能可靠判断已有登录。恢复流程改为先检查受保护的订单页。
- 用户第二次扫码后，保存会话并销毁/重建容器；22:28 的 `check-account --diagnostics` 明确输出“已复用官网登录状态，无需重新扫码”，随后完成未完成订单检查，退出码为 0。
- 修复重新打包后，22:31 直接运行最终镜像（不挂载开发源码）再次完成免扫码登录恢复及未完成订单检查，退出码为 0。检查容器随后退出，账号状态保留在原数据卷，未启动购票任务。
- 官网实际空状态为“您没有未完成的订单哦～”，位于 `.order-empty .empty-txt p`。其父容器还含其他说明，不能将父容器全部文本直接与空提示做等值比较；已修正，并限定 `#order_tab` 中“未完成订单”必须处于 active 状态。
- 本次验证没有点击“预订”、没有创建订单、没有付款。

## 成功标准

官方生成与配置一致的待支付订单，并及时通知用户付款；不重复下单，不将查询成功/点击成功/排队中误报为订票成功。单次成功也不等于证明抢票成功率提升。

## 低延迟版本与订单核对修订（2026-09-07）

- 当前共 78 项单元测试、9 个断网页面/乘车人场景及一个使用生产适配器的完整合成浏览器下单/回查流程通过。合成流程重开 SQLite 后总模拟提交次数为 1，不使用真实账号或网络。

- 新逻辑逐项验证行程、出发时刻、姓名/人数、成人票、席别、分配席位、金额和待支付状态，保存不含乘车人姓名的凭据；未显示订单号时不编造号码。

- 实测有界面模式可恢复此前登录；一次 headless 只读探测未确认登录，因此 Docker 保留原有有界面/虚拟显示器模式，不宣称两种模式的会话行为相同。
